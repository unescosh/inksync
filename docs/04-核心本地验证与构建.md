# 04 · 核心（Rust）本地验证与构建

> 适用场景：仅想在**没有 Visual Studio、也没有 MSYS2/mingw** 的 Windows 上把 `core/` 编出来跑单测，
> 验证解析与同步逻辑的正确性。三端**正式打包**走 `docs/03-三端适配与工程落地.md`（Android NDK / Windows MSVC / UOS 用 `cargo zigbuild …2.28`），
> 与本文件无关。
>
> 本环境（WorkBuddy 沙箱）就是这种「裸 Windows」：只有 rustup 的 `windows-gnu` 工具链，缺 mingw 的 `dlltool`/`as`，
> 因此用 **nightly + rust-lld** 绕过。这是验证手段，不是产品构建方式。

## 1. 安装工具链

```powershell
# rustup 自带（本机 ~/.cargo/bin/rustup.exe 可能是 0 字节代理，直接用绝对路径调用）
& "$env:USERPROFILE\.cargo\bin\rustup.exe" toolchain install nightly --profile minimal
```

正式编译时用 nightly：

```powershell
$TC = "$env:USERPROFILE\.rustup\toolchains\stable-x86_64-pc-windows-gnu"
# 真正的 cargo 在 toolchain 目录里（~/.cargo/bin 下的代理在某些环境是 0 字节）
$cargo = "$TC\bin\cargo.exe"
```

> 注意：`~/.cargo/bin/cargo.exe` 在部分安装里是 rustup 的 0 字节占位文件，
> 真正可用的 `cargo.exe`（约 58MB）位于
> `~/.rustup/toolchains/stable-x86_64-pc-windows-gnu/bin/cargo.exe`。
> 调用它即可，无需 PATH 代理。

## 2. 用 rust-lld 链接（关键）

`windows-gnu` 默认调用 mingw 的 `dlltool`/`as` 造导入库，裸机没有会报
`error calling dlltool 'dlltool.exe': program not found`。
nightly 支持 `-C linker-features=+lld`，让 rustc 用自带的 `rust-lld` 直接造导入库，
完全不碰 `dlltool`/`as`：

```powershell
$env:RUSTFLAGS = "-Z unstable-options -C link-self-contained=yes -C linker-features=+lld"
& $cargo +nightly build
& $cargo +nightly test
```

`link-self-contained=yes` 让 rustc 用 toolchain 自带的 `self-contained/ld.exe` 与 `rust-lld`，
不再依赖外部 binutils。

## 3. 运行单测

本环境（Git Bash / 沙箱）实测可用的完整调用（nightly 工具链绝对路径 + 自带 ld/rust-lld）：

```bash
TC=/c/Users/unesc/.rustup/toolchains/nightly-x86_64-pc-windows-gnu
CARGO=$TC/bin/cargo.exe
SELF=$TC/lib/rustlib/x86_64-pc-windows-gnu/bin/self-contained
export PATH="$SELF:$TC/bin:$PATH"
export RUSTFLAGS="-Z unstable-options -C link-self-contained=yes -C linker-features=+lld"
cd "C:/Users/unesc/Documents/workbuddy/inksync/core"
$CARGO test          # 26 unit + 4 integration，全绿（0 warning）
$CARGO build         # 默认 features（formats）纯 Rust 产物，0 warning
```

> 注意 `RUSTFLAGS` 里 `linker-features=+lld` 是 nightly 不稳定选项，必须带 `-Z unstable-options`。
> 若换 stable 工具链，这条链接方案不可用，需改用正式打包通道（见 `docs/03`）。

## 4. 已知校准点（开工前必查）

1. `mobi = "0.8"`（已校准）：`0.8.0` 的 `title()` 返回 `String`、`author/publisher/...` 返回 `Option<String>`，
   与旧文档里「9 个方法签名」提示不同，已按实际签名在 `core/src/formats/mobi.rs::read_meta_from_crate()` 写好。
2. `sync` feature 需要 C 编译器：默认 `default = ["formats"]`，**不**含同步依赖；
   `sync = ["dep:reqwest","dep:tokio","dep:bytes","dep:url"]`，开启后会拉 `rustls-tls` → `ring`（C/asm），
   在 Windows 上需要 mingw-w64 的 `gcc.exe`，在 UOS 上需要 `gcc`。
   **正式打包同步能力时，务必在带 C 工具链的环境编译，不要在本裸沙箱跑 `--features sync`。**
3. `flutter_rust_bridge = "2.0.0-dev.0"`：可选 feature，默认不开启；版本需与 `flutter_rust_bridge_codegen`
   严格匹配，真正接 Flutter 时再开。
4. `image = "0.25"`：默认 feature 已含 jpeg/png；若要 WebP 封面需显式加 `image = { version = "0.25", features = ["webp"] }`。
5. `zip` 只用 `deflate`、`flate2` 用 `miniz_oxide`（纯 Rust）：这是为绕开 `getrandom → bcryptprimitives` 链接坑
   做的刻意裁剪，升级依赖时不要顺手把 `zip` 的 `zstd`/`bzip2` 或 `uuid` 的 `v4` 加回来，否则裸 Windows 沙箱又会编不出。

## 5. 交叉编译到 UOS（glibc 2.28）

不走 nightly，走稳定 + `cargo-zigbuild`：

```powershell
& $cargo install cargo-zigbuild
& $cargo zigbuild --target x86_64-unknown-linux-gnu.2.28 --release
```

`zig` 自带 2.28 符号表，产物 `ldd`/`objdump -T` 查验所有 `GLIBC_*` ≤ 2.28 才放行（见 `docs/00-方案定稿.md` 第 10 节）。
