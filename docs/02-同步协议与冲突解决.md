# 02 · 同步协议与冲突解决

## 1. 约束：WebDAV 不是数据库

设计前必须承认四件事，否则一定踩坑：

1. **无事务**：多步写入随时中断。
2. **无锁**（部分服务端有 `LOCK`，但实现参差、超时语义混乱，**不要用**）。
3. **无推送**：没有 Webhook/WebSocket，"实时"只能靠轮询 + 事件触发。
4. **能力参差**：`If-Match`、`Expect: 100-continue`、`Content-Range`、分块上传各家实现不一。

由此推出三条设计底线：

- **只追加（append-only），不覆盖**：变更写入文件名唯一的新文件 → 并发写永不冲突。
- **大文件按内容寻址（sha256）**：同名即同内容，天然幂等、免冲突、可秒传。
- **唯一需要并发写的单文件（manifest）用 ETag 乐观锁 + 重试**。

## 2. 远端目录布局

```
/inksync/
├── manifest.json                      唯一可并发写的文件（ETag 乐观锁）
├── changes/
│   ├── 0000018A5F3C1A0-0003-7f3a…jsonl   文件名 = <HLC>-<deviceId前8位>
│   └── 0000018A5F3C1B2-0000-91c2…jsonl   HLC 字典序 = 全局时序
├── blobs/
│   └── ab/cdef1234…（原始书籍文件，内容寻址）
├── covers/
│   └── ab/cdef1234…（封面图片，内容寻址，与 blobs 完全镜像）
└── trash/                              软删除区（GC 时才真删）
```

`changes/` 里每个文件是一个**批次**（一次同步的所有本地变更），一行一条记录（JSONL，便于流式解析与断点）。

## 3. 数据记录格式

```jsonc
// changes/0000018A5F3C1A0-0003-7f3a.jsonl
{"t":"book","id":"b-9f2a…","op":"upsert","hlc":"0000018A5F3C1A0-0003-7f3a","node":"7f3a","d":{…}}
{"t":"progress","id":"b-9f2a…","op":"upsert","hlc":"…","node":"7f3a","d":{"percent":0.41,…}}
{"t":"rule","id":"r-quote","op":"upsert","hlc":"…","node":"7f3a","d":{…}}
{"t":"collection","id":"c-科幻","op":"delete","hlc":"…","node":"7f3a"}
```

`t` 取值：`book | progress | rule | collection | membership`。

> 封面**不单独成实体**：`coverHash` 随 `book` 的 upsert/deleted 一起同步（在 `d` 里），
> 封面**字节**单独走 `covers/`（见 §5 step 6b/7b）——把"元数据"和"大二进制"分开传，
> 避免封面图片（几 MB）塞进 changes/*.jsonl 拖慢每次同步与三方合并。

`d` 只放**完整快照**（不是 diff），因为书籍元数据小（<2KB），快照比增量更简单、更抗乱序。

`manifest.json`：

```jsonc
{ "schema": 1,
  "lastHlc": "0000018A5F3C1A0-0003-7f3a",
  "files": [ { "n": "0000018A5F3C1A0-0003-7f3a", "b": 4096, "d": "7f3a" } ],
  "updatedAt": "2026-09-02T04:12:03.221Z" }
```

> 生产环境 `files` 会膨胀。优化：manifest 只保留**近 200 个批次**，更老的按 `hlc` 前缀分桶成 `changes/index/<yyyy-mm>.json`，按需拉取（首次安装的冷启动除外）。

## 4. HLC（混合逻辑时钟）

不能用墙上时钟：三端系统时间可能差几分钟，NTP 也不保证。

**格式**：`{wall_ms:013X}-{counter:04X}-{node_hex:8}`
例：`0000018A5F3C1A0-0003-7f3a2b91`
→ **字典序 = 全序**，WebDAV 列目录按名排序即为时间序，无需解析时间。

**规则**（见 `core/src/sync/hlc.rs`）：

```
本地事件:  l = max(prev.wall, now_ms)
           c = (l == prev.wall) ? prev.c + 1 : 0
接收事件:  l = max(prev.wall, remote.wall, now_ms)
           c = match (l, prev.wall, remote.wall) {
               (x, x, x) => max(prev.c, remote.c) + 1,
               (x, x, _) => prev.c + 1,
               (x, _, x) => remote.c + 1,
               _         => 0 }
```

时钟偏移超过 ±60s 时给 HLC 打 `drift` 标记并在同步中心提示"本端系统时间可能不准"。

## 5. 同步流程

```
sync():
  0. 准备   确保目录结构存在（MKCOL，幂等，失败即报"目录不可写"）
  1. 拉清单 GET manifest.json（带 If-None-Match: <缓存 ETag>，命中 304 直接跳过 2~4）
  2. 列目录  PROPFIND /inksync/changes/  Depth:1  → 文件名列表 + ETag + size
  3. 下载    仅下载 hlc > lastAppliedHlc 且 node != 本端的批次文件
             （按名字排序，并发 ≤3，单文件失败重试 3 次后跳过并记账）
  4. 应用    逐条 JSONL：按 §6 冲突策略落库；更新 lastAppliedHlc
  5. 推送    outbox 中的**全部未推送记录**（即当前 outbox 表的全部行）→ 打包成一个批次
             PUT 到 changes/<hlc>.tmp → MOVE 到 changes/<hlc>   ← 原子发布
         ⚠️ outbox 是本地变更的「唯一事实来源」，推送后由第 9 步 `clearOutboxUpTo(seq)`
             按 seq 整体清空，**切忌**用 `hlc > lastPushedHlc`（或 `lastAppliedHlc`）去过滤！
             因为 `lastAppliedHlc` 在拉取远端批次后会被推进到本端 `clock.tick()` 的实时 HLC
             （~1.7e12），而本地变更 HLC 可能更小（固定测试 HLC、本端时钟回拨），一旦
             `hlc ≤ lastAppliedHlc` 就被误判为"已同步"而**永久丢弃**——典型受害者是墓碑删除，
             导致书籍/分组/规则删除永远推不出去、跨端不同步（见 `docs/08` 的「墓碑跨端不同步」）。
             **HLC 只用于冲突裁决（LWW），绝不用于"是否已推送"的水位线。**
  6. 传文件  对每个待上传 book：PROPFIND blobs/ab/<sha256> 存在则秒传跳过
             否则 PUT 临时名 → 校验 → MOVE 到最终名
  6b. 传封面 与传文件**完全镜像**（见 `SyncEngine._transferCovers`）：
             coverHash 非空且本地有封面的书 →
             PROPFIND covers/ab/<hash> 存在则跳过，否则 PUT 字节；
             内容寻址，同名即同内容，天然幂等、可秒传
  7. 拉文件  本地缺 blob 的书：按 sha256 下载 → 校验 sha256 → 落盘
             （失败保留 .part，下次续传；校验失败删除重下）
  7b. 拉封面 本地 coverPath 为空、但 coverHash 非空的书（典型：B 端只收到
             了 coverHash 元数据、从没拥有封面文件）：按 coverHash 下载
             → 校验 sha256 → 落盘到 <cacheDir>/covers/<hash>.<ext>
             （扩展名由图片魔数探测）→ 回填 book.coverPath，书架才显示
  8. 写清单  PUT manifest.json 带 If-Match: <第1步的 ETag>
             412 → 重跑 1~8（最多 5 次，指数退避）
  9. 收尾    清 outbox（seq ≤ 最后推送）、更新 UI、记录 SyncReport
```

**幂等性**：任何一步中断，重跑都安全——批次文件名由 HLC 决定（重跑产生新的、更大的 HLC，不会覆盖旧文件），blob 内容寻址，落库按 `(id, hlc)` 比较跳过更旧的。

### 5.1 "实时"如何达成

WebDAV 没有推送，所以分三层：

| 触发 | 时机 | 成本 |
|---|---|---|
| **事件触发（主）** | 翻页停止 2s / 加书 / 改规则 / 改分组 → 写 outbox → **debounce 3s 后**触发一次同步 | 一次同步 ≈ 2~4 个请求 |
| **轻量轮询（兜底）** | 阅读中 60s；空闲 5min；App 回前台立即 | 命中 304 时仅 1 个请求、~200B |
| **周期任务（Android）** | WorkManager 15min（系统下限） + 充电/联网约束 | 后台 |
| **可选增强** | 自建 WebSocket 通知服务（仅做"有人改了"的信号，数据仍走 WebDAV） | 秒级 |

真实体验：三端同时开着，一次翻页到另一端看到更新 ≈ 3~8 秒。这已足够。

### 5.2 Rust 原生传输层（无 Flutter 依赖）

Dart `SyncEngine` 里的 `_transferBlobs` / `_transferCovers` 逻辑，在 Rust 核心有**逐条对齐**的镜像实现
（`core/src/sync/transfer.rs`），供 UOS / CLI 这类**不加载 Flutter 引擎**的路径原生同步书与封面字节：

- `transfer_blobs` / `transfer_covers(fs, cfg, remote_root, entries, store, report, on_downloaded)`：
  循环体内逻辑与 Dart 完全一致——本地有+远端缺→`put_atomic`+计数；本地缺+远端有→
  `get_bytes`+**sha256 校验**+落盘+回调 `on_downloaded`+计数；校验不符丢弃；二次同步幂等。
- **不耦合数据库**：Rust 核心无 drift，函数接收调用方传入的待传条目列表（`BlobEntry` / `CoverEntry`），
  取数与落库（回填 `localPath` / `coverPath`）交给未来的 Rust SyncEngine / CLI 通过 `on_downloaded` 回调完成。
- **可单测**：通过 `DavFs` trait 接缝把具体 WebDAV 实现隔离；真实 `WebDavClient` 仅在 `sync` feature 下
  `impl DavFs`，`transfer` 模块本身**不门控**，故默认 `cargo test`（沙箱/CI 都编不过 `sync` feature）即可
  编译并跑通单测。`SyncReport.uploaded_covers` / `downloaded_covers` 即由本模块产出。

> 若用户同时用 Nextcloud，可额外接 `Nextcloud` 的 `ocs/v2.php/apps/serverinfo` … 不推荐，破坏协议中立性。**坚持只用标准 WebDAV 方法**（`PROPFIND/GET/PUT/DELETE/MKCOL/MOVE/COPY`），兼容性最好。

#### 5.2.1 无头 CLI（`core/examples/cli_backup.rs`，`required-features = ["sync"]`）

把 §5.2 的传输层直接接上一个最小命令行入口，让 UOS / 服务器 / CI 能**不依赖 Flutter 引擎**做备份与恢复：

- `push`：`scan_book_dir(书目录)` 递归扫出 `BlobEntry`（书名=文件名、sha256 流式算）→ `pair_covers(books, 封面目录)` 按「文件名（去扩展名）」配对 `CoverEntry` → `transfer_blobs` / `transfer_covers` 推到远端。
- `pull`：`list_remote(fs, cfg, remote_root)` 枚举远端 `blobs/` `covers/` 下所有内容寻址条目 → 构造 `local_path=None` 的条目 → 调同一对 `transfer_*` 函数把本地仓库缺的拉回 `--store`（经 `FsBlobStore` / `FsCoverStore` 落盘，sha256 校验）。
- 两个模式都走同一套 `transfer_blobs` / `transfer_covers` + `DavFs` 接缝，行为、校验、幂等性与 Dart 引擎完全一致；CLI 只是扫描/配对/枚举这层薄胶水。
- 编排已下沉到 lib（`core/src/sync/transfer.rs`，默认 features、可单测），CLI 只做参数组装：
  - `sync_local_books(fs, cfg, remote_root, books_dir, covers_dir, blob_store, cover_store, report, on_downloaded)`：一次完整推送（scan → pair → transfer），返回扫描条目；
  - `pull_remote(fs, cfg, remote_root, blob_store, cover_store, report, on_downloaded)`：一次完整拉取（list_remote → transfer 缺失项）；
  - `BookIndex`（`book_index.json`）：push 后把内容寻址的 `sha256`/`coverHash` 映射回书名写进 `<store>/book_index.json`，便于无头备份后核对"备份了哪些书"；`BookIndex::from_scan` / `write_to` / `read_from` 为纯 serde，沙箱/CI 默认 `cargo test` 可单测。

```text
cargo run --features sync --example cli_backup -- push \
    --books /path/to/books --covers /path/to/covers --store /path/to/store \
    --url https://dav.example.com/inksync/ --user alice --pass secret
```

**配置文件（避免命令行明文传密码）**：`--config <path>`（或 `--env <path>`）读取 `KEY=VALUE` 文件；命令行参数优先级高于配置文件。支持的键：`INKSYNC_URL` / `INKSYNC_USER` / `INKSYNC_PASS` / `INKSYNC_BOOKS` / `INKSYNC_COVERS` / `INKSYNC_STORE` / `INKSYNC_REMOTE`。解析逻辑放在 `core/src/cli.rs`（默认 features、纯 std，可在沙箱/CI 默认 `cargo test` 下单测），不与 `sync` 门控的 example 耦合。

```text
# inksync.env
INKSYNC_URL=https://dav.example.com/inksync/
INKSYNC_USER=alice
INKSYNC_PASS=secret
INKSYNC_BOOKS=/path/to/books
INKSYNC_COVERS=/path/to/covers
INKSYNC_STORE=/path/to/store

cargo run --features sync --example cli_backup -- push --config ./inksync.env
```

**`--dry-run`**：只打印将要上传/下载的内容，不触碰远端。push 完全本地（扫描+配对后列出书名/sha256/coverHash）；pull 只读远端枚举（list_remote）列出 blob/cover 哈希。便于在 UOS 上确认计划再正式执行。

**`verify`**（本地自检，不需要网络）：逐个重算 `--store` 下 `blobs/` 与 `cache/covers/` 每个文件的 sha256，与内容寻址文件名比对，抓出磁盘静默损坏 / 半截文件；全部通过退出码 0，有损坏退出码 1。实现见 `transfer.rs` 的 `verify_store`（默认 features、可在沙箱/CI 单测）。建议接在定时备份之后跑。

> 该 example 必须 `--features sync`（要 `WebDavClient` 联网）；沙箱/CI 的 Rust job 跑默认 features（不编 `sync`），故 CLI 本身不在 CI 编译范围内——其底层传输逻辑由 `core/src/sync/transfer.rs` 的 `cli_scan_pair_and_transfer` 等内存单测在默认 features 下覆盖；`.env` 解析由 `core/src/cli.rs` 单测覆盖。完整运维用法（编译、配置、systemd 定时备份）见 `docs/09-无头CLI使用指南.md`。

#### 5.2.2 Flutter 端本地仓库对齐（`reconcileLocalRepo`）

无头 `pull` 把书文件与封面直接写进 `<appDocDir>/blobs/...` 与 `<appDocDir>/cache/covers/...`（路径刻意与 `DefaultBlobStore` / `DefaultCoverStore` 对齐，Rust 侧 `FsBlobStore` / `FsCoverStore` 也按此布局落盘），但 App 主库（`books` 表）的 `localPath` / `coverPath` 是**后填的可空缓存列**——无头 `pull` 不经过 `_transferBlobs` / `_transferCovers` 的回填分支，所以这两列仍是空。书架 UI 读到空列会误判"未下载"。

`SyncEngine.reconcileLocalRepo()` 负责把这个缺口补上：

- 遍历 `db.books`；
- 若 `sha256` 非空且 `localPath` 为空 → `blobs.pathFor(sha256)`，命中且 `File` 真实存在则回写 `localPath`；
- 若 `coverHash` 非空且 `coverPath` 为空 → `covers.pathFor(coverHash)`，命中且存在则回写 `coverPath`。

它被 `_syncOnce` 的 **5c 步**调用（在 `_transferBlobs` / `_transferCovers` 之后），日常同步也无害：文件已存在则命中列本非空、不会重复写；空列则被补齐。也可由 App 在无头 `pull` 完成后单独调用一次，立即让书架显示"已下载"。

> 回归测试：`app/test/cross_end_test.dart` 的 **T8** 用例用内存 SQLite + `_SeededBlobStore` / `FakeCoverStore`（预置已落地文件）验证：reconcile 后 `localPath` / `coverPath` 被回写为真实路径、文件存在，且重复调用幂等；完整 `sync()` 的 5c 步走到同一逻辑不报错。

## 6. 冲突解决策略矩阵

**核心思想：不同数据用不同策略。一律 LWW 会导致"读到一半进度被回退"这种致命体验。**

| 数据 | 策略 | 理由 |
|---|---|---|
| 书籍文件（blob） | 内容寻址，无冲突 | 文件不可变 |
| 封面图片（cover blob） | 内容寻址，无冲突（镜像书籍文件） | 文件不可变，按 sha256 跨端传输+校验，路径回填到 coverPath |
| 书籍元数据（title/author/tags…） | **字段级 LWW**（比较 HLC，相等则比 deviceId 字典序） | 用户改名/改封面，后改的赢，符合直觉 |
| 自定义封面 | LWW（同元数据） | 后设的赢 |
| **阅读进度** | **`forced ? LWW : max(percent)`** | 用户通常想接续最远进度；但**手动跳转（拖进度条/目录跳转）标 `forced=true`**，此时必须 LWW 覆盖，否则拖不回去 |
| 分组（collection）名称/顺序 | LWW | — |
| 分组成员关系（membership） | **LWW + 并集倾向**：两端各自"加入分组"取并集；"移除"才算删除 | 避免一端加的书被另一端的旧快照抹掉 |
| 高亮规则 | LWW per rule（同 id） | 规则改了就是改了 |
| 删除 | **墓碑（tombstone）优先**，保留 90 天 | 防止离线端"复活"已删的书 |
| 排序偏好（sortKey/sortDir/groupBy） | **不同步，纯本地** | 三端屏幕差异大，桌面想要列表、手机想要网格，强制同步反而糟糕 |

### 6.1 三方合并（three-way merge）

纯 LWW 在"两端基于同一旧版本各自修改**不同字段**"时会丢数据。因此对每个实体保留一个 `baseSnapshot`（上次同步成功时的值），合并时：

```
merge(local, remote, base):
  for each field f in schema:
    localChanged  = local.f  != base.f
    remoteChanged = remote.f != base.f
    if  localChanged &&  remoteChanged → 用 LWW（HLC）裁决，并把败者写入 conflict_log（可供用户"查看被覆盖的值"）
    if  localChanged && !remoteChanged → 保留 local
    if !localChanged &&  remoteChanged → 采用 remote
    else                               → 不动
```

`base` 的维护成本：每次同步成功后把当前值复制一份到 `*_base` 表（或存 `baseJson` 列），只保留最近一次。空间开销可接受（1 万本书 ≈ 8MB）。

### 6.2 冲突可见化

不做静默覆盖。所有被裁决掉的写入进入 `conflict_log`：

```
conflict_log(id, entityType, entityId, field, localValue, remoteValue, winnerHlc, resolvedAt, dismissed)
```

同步中心显示"本次同步有 2 处冲突"，点开可**一键采用本端 / 采用远端**。这是数据安全的最后一道保险。

## 7. 传输层细节（血泪清单）

| 坑 | 处理 |
|---|---|
| 中文/空格路径 | 每段路径单独 `percent-encode`（保留 `/`） |
| `PROPFIND` 必须带 `Depth: 1` | 否则部分服务端返回空 |
| 207 响应 `href` 可能是绝对 URL 且主机名不同 | 用 `path` 做匹配，不比对 host |
| `Expect: 100-continue` 导致 1s 延迟/失败 | 显式关闭（dio: `options.headers.remove('Expect')`） |
| 大文件上传中断 | WebDAV 普遍不支持 `Content-Range` 追加 → 采用「PUT 临时文件 + 校验 + MOVE」；>50MB 时在 UI 上明确提示"不建议用 WebDAV 传超大文件" |
| 自签名证书（群晖/内网） | 提供"信任此证书"开关 + 证书指纹固定（pinning），dio `badCertificateCallback` |
| 429 / 503（坚果云限流） | 指数退避 + 抖动，尊重 `Retry-After` |
| 坚果云/阿里云盘 WebDAV 不支持 `MOVE` | 降级为 `COPY + DELETE`，失败再降级为 `PUT + DELETE` |
| 覆盖写导致半截文件 | 一律 `PUT → 临时名`，成功校验后再 `MOVE` |
| 目录不存在 | 首次同步递归 `MKCOL`，`405 Method Not Allowed` 视为已存在 |
| 时钟漂移 | HLC 检测 + 提示 |

## 8. 安全

- 凭据存系统安全区：Android `EncryptedSharedPreferences`/Keystore、Windows `Credential Manager`(`win32` DPAPI)、Linux `libsecret`。
- **可选端到端加密**：口令 → Argon2id → AES-256-GCM。加密后：`blobs/*` 整体加密（书名不泄露），`changes/*.jsonl` 与 `manifest.json` 的 `d` 字段加密（仅保留 `t/op/hlc` 明文以便排序）。开启后无法在网页端浏览，属权衡项。
- 只读模式：同步设置可设"仅拉取"，防止误操作覆盖服务端。

## 9. 垃圾回收

- `changes/` 批次：被所有已知 device 应用且超过 **30 天** → 移入 `trash/`（保留 60 天后真删）。
- `blobs/`：无任何 book 记录引用（含墓碑 90 天内）→ 移入 `trash/`。
- GC 只在"最活跃节点"执行（manifest 里记录各 device 最后活跃时间），且**每次 GC 前先 PUT 一个 `gc-lock-<hlc>` 文件**并在下次同步校验，避免多端同时 GC。
- 冷启动（新设备）：跳过 GC，直接按 `changes/` 全量重放；若批次 > 500 个，先生成一次合并快照 `changes/snapshot-<hlc>.jsonl`（压缩后）加速。
