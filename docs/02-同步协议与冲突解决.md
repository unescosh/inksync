# 02 · 同步协议与冲突解决

## 1. 约束：WebDAV 不是数据库

设计前必须承认四件事，否则一定踩坑：

1. **无事务**：多步写入随时中断。
2. **无锁**（部分服务端有 `LOCK`，但实现参差、超时语义混乱，**不要用**）。
3. **无推送**：没有 Webhook/WebSocket，"实时"只能靠轮询 + 事件触发。
4. **能力参差**：`If-Match`、`Expect: 100-continue`、`Content-Range`、分块上传各家实现不一。

由此推出三条设计底线：

- **只追加（append-only），不覆盖**：变更写入文件名唯一的新文件 → 并发写永不冲突。
- **大文件按内容寻址（sha256）**：同名即同内容，天然幂等、免冲突、可秒传。
- **唯一需要并发写的单文件（manifest）用 ETag 乐观锁 + 重试**。

## 2. 远端目录布局

```
/inksync/
├── manifest.json                      唯一可并发写的文件（ETag 乐观锁）
├── changes/
│   ├── 0000018A5F3C1A0-0003-7f3a…jsonl   文件名 = <HLC>-<deviceId前8位>
│   └── 0000018A5F3C1B2-0000-91c2…jsonl   HLC 字典序 = 全局时序
├── blobs/
│   └── ab/cdef1234…（原始书籍文件，内容寻址）
├── covers/
│   └── <bookId>-<coverSha256>.jpg
└── trash/                              软删除区（GC 时才真删）
```

`changes/` 里每个文件是一个**批次**（一次同步的所有本地变更），一行一条记录（JSONL，便于流式解析与断点）。

## 3. 数据记录格式

```jsonc
// changes/0000018A5F3C1A0-0003-7f3a.jsonl
{"t":"book","id":"b-9f2a…","op":"upsert","hlc":"0000018A5F3C1A0-0003-7f3a","node":"7f3a","d":{…}}
{"t":"progress","id":"b-9f2a…","op":"upsert","hlc":"…","node":"7f3a","d":{"percent":0.41,…}}
{"t":"rule","id":"r-quote","op":"upsert","hlc":"…","node":"7f3a","d":{…}}
{"t":"collection","id":"c-科幻","op":"delete","hlc":"…","node":"7f3a"}
```

`t` 取值：`book | progress | rule | collection | membership | cover`。
`d` 只放**完整快照**（不是 diff），因为书籍元数据小（<2KB），快照比增量更简单、更抗乱序。

`manifest.json`：

```jsonc
{ "schema": 1,
  "lastHlc": "0000018A5F3C1A0-0003-7f3a",
  "files": [ { "n": "0000018A5F3C1A0-0003-7f3a", "b": 4096, "d": "7f3a" } ],
  "updatedAt": "2026-09-02T04:12:03.221Z" }
```

> 生产环境 `files` 会膨胀。优化：manifest 只保留**近 200 个批次**，更老的按 `hlc` 前缀分桶成 `changes/index/<yyyy-mm>.json`，按需拉取（首次安装的冷启动除外）。

## 4. HLC（混合逻辑时钟）

不能用墙上时钟：三端系统时间可能差几分钟，NTP 也不保证。

**格式**：`{wall_ms:013X}-{counter:04X}-{node_hex:8}`
例：`0000018A5F3C1A0-0003-7f3a2b91`
→ **字典序 = 全序**，WebDAV 列目录按名排序即为时间序，无需解析时间。

**规则**（见 `core/src/sync/hlc.rs`）：

```
本地事件:  l = max(prev.wall, now_ms)
           c = (l == prev.wall) ? prev.c + 1 : 0
接收事件:  l = max(prev.wall, remote.wall, now_ms)
           c = match (l, prev.wall, remote.wall) {
               (x, x, x) => max(prev.c, remote.c) + 1,
               (x, x, _) => prev.c + 1,
               (x, _, x) => remote.c + 1,
               _         => 0 }
```

时钟偏移超过 ±60s 时给 HLC 打 `drift` 标记并在同步中心提示"本端系统时间可能不准"。

## 5. 同步流程

```
sync():
  0. 准备   确保目录结构存在（MKCOL，幂等，失败即报"目录不可写"）
  1. 拉清单 GET manifest.json（带 If-None-Match: <缓存 ETag>，命中 304 直接跳过 2~4）
  2. 列目录  PROPFIND /inksync/changes/  Depth:1  → 文件名列表 + ETag + size
  3. 下载    仅下载 hlc > lastAppliedHlc 且 node != 本端的批次文件
             （按名字排序，并发 ≤3，单文件失败重试 3 次后跳过并记账）
  4. 应用    逐条 JSONL：按 §6 冲突策略落库；更新 lastAppliedHlc
  5. 推送    outbox 中 `hlc > lastPushedHlc` 的记录 → 打包成一个批次
             PUT 到 changes/<hlc>.tmp → MOVE 到 changes/<hlc>   ← 原子发布
  6. 传文件  对每个待上传 book：PROPFIND blobs/ab/<sha256> 存在则秒传跳过
             否则 PUT 临时名 → 校验 → MOVE 到最终名
  7. 拉文件  本地缺 blob 的书：按 sha256 下载 → 校验 sha256 → 落盘
             （失败保留 .part，下次续传；校验失败删除重下）
  8. 写清单  PUT manifest.json 带 If-Match: <第1步的 ETag>
             412 → 重跑 1~8（最多 5 次，指数退避）
  9. 收尾    清 outbox（seq ≤ 最后推送）、更新 UI、记录 SyncReport
```

**幂等性**：任何一步中断，重跑都安全——批次文件名由 HLC 决定（重跑产生新的、更大的 HLC，不会覆盖旧文件），blob 内容寻址，落库按 `(id, hlc)` 比较跳过更旧的。

### 5.1 "实时"如何达成

WebDAV 没有推送，所以分三层：

| 触发 | 时机 | 成本 |
|---|---|---|
| **事件触发（主）** | 翻页停止 2s / 加书 / 改规则 / 改分组 → 写 outbox → **debounce 3s 后**触发一次同步 | 一次同步 ≈ 2~4 个请求 |
| **轻量轮询（兜底）** | 阅读中 60s；空闲 5min；App 回前台立即 | 命中 304 时仅 1 个请求、~200B |
| **周期任务（Android）** | WorkManager 15min（系统下限） + 充电/联网约束 | 后台 |
| **可选增强** | 自建 WebSocket 通知服务（仅做"有人改了"的信号，数据仍走 WebDAV） | 秒级 |

真实体验：三端同时开着，一次翻页到另一端看到更新 ≈ 3~8 秒。这已足够。

> 若用户同时用 Nextcloud，可额外接 `Nextcloud` 的 `ocs/v2.php/apps/serverinfo` … 不推荐，破坏协议中立性。**坚持只用标准 WebDAV 方法**（`PROPFIND/GET/PUT/DELETE/MKCOL/MOVE/COPY`），兼容性最好。

## 6. 冲突解决策略矩阵

**核心思想：不同数据用不同策略。一律 LWW 会导致"读到一半进度被回退"这种致命体验。**

| 数据 | 策略 | 理由 |
|---|---|---|
| 书籍文件（blob） | 内容寻址，无冲突 | 文件不可变 |
| 书籍元数据（title/author/tags…） | **字段级 LWW**（比较 HLC，相等则比 deviceId 字典序） | 用户改名/改封面，后改的赢，符合直觉 |
| 自定义封面 | LWW（同元数据） | 后设的赢 |
| **阅读进度** | **`forced ? LWW : max(percent)`** | 用户通常想接续最远进度；但**手动跳转（拖进度条/目录跳转）标 `forced=true`**，此时必须 LWW 覆盖，否则拖不回去 |
| 分组（collection）名称/顺序 | LWW | — |
| 分组成员关系（membership） | **LWW + 并集倾向**：两端各自"加入分组"取并集；"移除"才算删除 | 避免一端加的书被另一端的旧快照抹掉 |
| 高亮规则 | LWW per rule（同 id） | 规则改了就是改了 |
| 删除 | **墓碑（tombstone）优先**，保留 90 天 | 防止离线端"复活"已删的书 |
| 排序偏好（sortKey/sortDir/groupBy） | **不同步，纯本地** | 三端屏幕差异大，桌面想要列表、手机想要网格，强制同步反而糟糕 |

### 6.1 三方合并（three-way merge）

纯 LWW 在"两端基于同一旧版本各自修改**不同字段**"时会丢数据。因此对每个实体保留一个 `baseSnapshot`（上次同步成功时的值），合并时：

```
merge(local, remote, base):
  for each field f in schema:
    localChanged  = local.f  != base.f
    remoteChanged = remote.f != base.f
    if  localChanged &&  remoteChanged → 用 LWW（HLC）裁决，并把败者写入 conflict_log（可供用户"查看被覆盖的值"）
    if  localChanged && !remoteChanged → 保留 local
    if !localChanged &&  remoteChanged → 采用 remote
    else                               → 不动
```

`base` 的维护成本：每次同步成功后把当前值复制一份到 `*_base` 表（或存 `baseJson` 列），只保留最近一次。空间开销可接受（1 万本书 ≈ 8MB）。

### 6.2 冲突可见化

不做静默覆盖。所有被裁决掉的写入进入 `conflict_log`：

```
conflict_log(id, entityType, entityId, field, localValue, remoteValue, winnerHlc, resolvedAt, dismissed)
```

同步中心显示"本次同步有 2 处冲突"，点开可**一键采用本端 / 采用远端**。这是数据安全的最后一道保险。

## 7. 传输层细节（血泪清单）

| 坑 | 处理 |
|---|---|
| 中文/空格路径 | 每段路径单独 `percent-encode`（保留 `/`） |
| `PROPFIND` 必须带 `Depth: 1` | 否则部分服务端返回空 |
| 207 响应 `href` 可能是绝对 URL 且主机名不同 | 用 `path` 做匹配，不比对 host |
| `Expect: 100-continue` 导致 1s 延迟/失败 | 显式关闭（dio: `options.headers.remove('Expect')`） |
| 大文件上传中断 | WebDAV 普遍不支持 `Content-Range` 追加 → 采用「PUT 临时文件 + 校验 + MOVE」；>50MB 时在 UI 上明确提示"不建议用 WebDAV 传超大文件" |
| 自签名证书（群晖/内网） | 提供"信任此证书"开关 + 证书指纹固定（pinning），dio `badCertificateCallback` |
| 429 / 503（坚果云限流） | 指数退避 + 抖动，尊重 `Retry-After` |
| 坚果云/阿里云盘 WebDAV 不支持 `MOVE` | 降级为 `COPY + DELETE`，失败再降级为 `PUT + DELETE` |
| 覆盖写导致半截文件 | 一律 `PUT → 临时名`，成功校验后再 `MOVE` |
| 目录不存在 | 首次同步递归 `MKCOL`，`405 Method Not Allowed` 视为已存在 |
| 时钟漂移 | HLC 检测 + 提示 |

**服务端兼容矩阵**（需在 M5 逐个实测）：

| 服务端 | PROPFIND | MOVE | If-Match | 备注 |
|---|---|---|---|---|
| Nextcloud / ownCloud | ✅ | ✅ | ✅ | 支持 `OC-Chunked` 分块，可选优化 |
| 群晖 DSM WebDAV | ✅ | ✅ | ✅ | 注意自签证书 |
| 坚果云 | ✅ | ✅ | ⚠️ | 有频率限制，需退避 |
| 阿里云盘（WebDAV 网关） | ✅ | ⚠️ | ❌ | 需降级路径 |
| Box.com | ✅ | ✅ | ✅ | 中文文件名有坑 |
| wsgidav（本地测试） | ✅ | ✅ | ✅ | CI 用它做集成测试 |

## 8. 安全

- 凭据存系统安全区：Android `EncryptedSharedPreferences`/Keystore、Windows `Credential Manager`(`win32` DPAPI)、Linux `libsecret`。
- **可选端到端加密**：口令 → Argon2id → AES-256-GCM。加密后：`blobs/*` 整体加密（书名不泄露），`changes/*.jsonl` 与 `manifest.json` 的 `d` 字段加密（仅保留 `t/op/hlc` 明文以便排序）。开启后无法在网页端浏览，属权衡项。
- 只读模式：同步设置可设"仅拉取"，防止误操作覆盖服务端。

## 9. 垃圾回收

- `changes/` 批次：被所有已知 device 应用且超过 **30 天** → 移入 `trash/`（保留 60 天后真删）。
- `blobs/`：无任何 book 记录引用（含墓碑 90 天内）→ 移入 `trash/`。
- GC 只在"最活跃节点"执行（manifest 里记录各 device 最后活跃时间），且**每次 GC 前先 PUT 一个 `gc-lock-<hlc>` 文件**并在下次同步校验，避免多端同时 GC。
- 冷启动（新设备）：跳过 GC，直接按 `changes/` 全量重放；若批次 > 500 个，先生成一次合并快照 `changes/snapshot-<hlc>.jsonl`（压缩后）加速。
