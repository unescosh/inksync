# M3 同步引擎 · 代码审核报告

> 审核范围：`app/lib/sync/*`、`app/lib/data/database.dart`、`app/lib/state/providers.dart`、
> `app/lib/screens/{reader_screen,rules_screen,library_screen}.dart`、`app/lib/reader/rules.dart`
> 视角：软件开发工程师（正确性 / 健壮性 / 一致性），不跑工具链（本机无 Flutter/Rust，验证靠 CI）。

## 0. 总体评价

**架构是好的，落地有缺口。** 设计层面的决策都很扎实：

- HLC 定宽编码（`{wallMs}-{counter}-{node}`），字典序即时间序 —— 正确且优雅。
- WebDAV 客户端硬化充分：逐段 percent-encode、207 MultiStatus 解析、MKCOL 405→成功、
  MOVE 不支持降级 COPY+DELETE、PUT 临时名→MOVE 正式名（无半截文件）、ETag+If-Match 乐观锁 + 412 重试。
- 三方字段级合并 + 墓碑软删 + 冲突留痕（`conflictLog`）的思路是对的，比纯 LWW 体验好很多。
- 写库 → 入 outbox → `markDirty()` 的链路在**五类实体上全部存在**（见 §6 更正）。

但**合并层语义 + outbox payload schema 两处没对齐规范实体 map**，导致以下静默数据损坏 / 首同步失败。
其中 C1 是上线阻断级，H1–H5 是高危。

## 1. 【CRITICAL】首次同步必失败：`getIfChanged` 对 404 抛异常

- **位置**：`webdav_client.dart:197-200`
  ```dart
  if (resp.statusCode == 304) return null;
  if (resp.statusCode == 404) {
    throw WebDavException(404, '资源不存在: $path');   // ← 问题在这
  }
  ```
- **调用链**：`sync_engine.dart:191` `final got = await client.getIfChanged(_manifestPath, cachedEtag);`
  在 `_syncOnce` 第 1 步拉 manifest。
- **根因 / 影响**：全新用户第一次同步时远端**还没有** `manifest.json`，服务端回 404。
  `getIfChanged` 抛 `WebDavException(404)`，被 `sync()` 的 catch 捕获（`sync_engine.dart:170`）→
  记进 `report.errors` 并 `break`。**结果是：任何一个新设备永远无法完成首次同步。**
- **修复**（一行）：404 视为"远端还没有 manifest"，返回 `null`，让 `_syncOnce` 走已有的空 manifest 分支：
  ```dart
  if (resp.statusCode == 304) return null;
  if (resp.statusCode == 404) return null; // 首次同步：manifest 尚不存在，等同空
  ```
  注：同文件 `propfind`（`:162`）对 404 就是 `return const []`，此处行为不一致，应统一为"404=空"。

## 2. 【HIGH】`mergeEntity` 把"远端缺字段"当成"置空" → 稀疏 payload 覆盖未改字段

- **位置**：`merge.dart:74-104`，核心在 `else if (remoteChanged) { out[k] = rv; }`（`:98`）。
- **根因**：合并遍历 `{...local.keys, ...remote.keys}`。当某字段**远端 payload 没带**（即"远端没改它"），
  `rv = remote[k] = null`，而 `remoteChanged = !_eq(null, baseValue)` 在非空 base 下为 `true`
  → 走到 `out[k] = rv = null`，把本地未改的字段**清空**。
- **具体表现**：
  - `reorderCollections`（`providers.dart:561`）的 outbox 只发 `{id, sortOrder}`。
    接收端本地分组有 `name/colorValue/emoji`，base 也有 → 这三个字段被置 `null`/`''`。
    **后果：分组顺序一同步，分组名就变空了。**（`colorValue`/`emoji` 同理被清。）
  - `importBook` 的 payload 省略 `coverPath/localPath/coverSource`，已存在的书再同步时封面被清。
- **修复（根因级）**：区分"远端缺字段"与"远端显式置空"：
  ```dart
  for (final k in keys) {
    if (_metaKeys.contains(k)) continue;
    final remoteHas = remote.containsKey(k);   // 新增
    final lv = local[k];
    final rv = remote[k];
    final bv = base?[k];
    if (!remoteHas) {
      out[k] = lv ?? bv;   // 远端没动 → 保本地，绝不置空
      continue;
    }
    final localChanged = !_eq(lv, bv);
    final remoteChanged = !_eq(rv, bv);
    // ……原有冲突分支不变……
  }
  ```
  这一处修好，`reorderCollections` 的覆盖、封面被清等问题**自动消失**。

## 3. 【HIGH】书籍标签 `tags` 不同步（payload schema 与规范 map 不一致）

- **位置**：`providers.dart:480` 写 outbox 用 `'tags': probe.tags`（List）；
  `sync_engine.dart:612` `_bookCompanion` 读 `m['tagsJson']`（JSON 字符串）。
- **影响**：`importBook` 推上去的是 `tags`（数组），接收端合并后写库时 `tagsJson` 为 `null` → 默认 `'[]'`。
  **用户打的书签/标签在同步后丢失。**（`_bookToMap` 用的是 `tagsJson`，所以规范 schema 是字符串。）
- **修复**：把 payload 改成与规范 map 一致：
  ```dart
  'tagsJson': jsonEncode(probe.tags),   // 替换原来的 'tags': probe.tags
  ```

## 4. 【HIGH】阅读进度同步到新设备会崩 / 落空（缺 `bookId`）

- **位置**：`reader_screen.dart:226-233` 的 progress payload **没有 `bookId`**；
  `sync_engine.dart:642` `_progressCompanion` 要求 `m['bookId'] as String`（非 null）。
- **影响**：当一台设备**第一次**收到某本书的进度（`local == null`），`_mergeInto` 走直接写分支
  （`sync_engine.dart:406-413`）把远端 payload 直接喂给 `_progressCompanion` → `null as String` 抛
  `CastError`（或被 NOT NULL 约束挡下）。**进度无法同步到新设备。**
- **修复**：在 `reader_screen` 编码前补上 bookId：
  ```dart
  payload['bookId'] = widget.bookId;   // 加在 jsonEncode(payload) 之前
  ```

---

## 5. 【HIGH】高亮规则删除不同步（delete payload 缺 `deleted`）

- **位置**：`rules_screen.dart:544` 删除 payload 为 `jsonEncode({'id': rule.id})`；
  `merge.dart:56` `mergeEntity` 仅靠 `remote['deleted'] == true` 判定删除。
- **影响**：删除被误判为一次普通 upsert：
  - 本地已存在该规则 → 字段被置空 / 名字变 `''`，且**保持未删除**（复活）；
  - 本地不存在 → 甚至据此 **插入一条空白规则**。
  **"删规则"在同步后等于"制造垃圾规则"。**
- **修复**：与 book 墓碑一致，delete payload 必须带 `deleted:true`：
  ```dart
  payloadJson: jsonEncode({
    'id': rule.id,
    'deleted': true,
    'hlc': hlc.encode(),
    'updatedBy': deviceId,
  }),
  ```
  > 顺带提醒：`op`（'delete'/'upsert'）虽传入 `_mergeInto`，但合并层完全没用它，
  > 删除判定只看 `remote['deleted']`。这是当前设计的隐含契约，所有 delete payload 都要遵守。

## 6. 【HIGH】高亮规则作用域 `scope` 不同步（`scope` List vs `scopeCsv` string）

- **位置**：`rules_screen.dart:496` 用 `row.toJson()` 作为 payload；
  `rules.dart:90` `toJson` 输出 `'scope': <List>`；而 `sync_engine.dart:688`
  `_ruleCompanion` 读 `m['scopeCsv']`（逗号串）。
- **影响**：接收端 `scopeCsv` 为 `null` → 默认 `'novel'`。**规则的作用域（漫画/小说/双端）在同步后丢失。**
- **修复（不动 `toJson`，避免波及其它调用方）**：在 `rules_screen` 构造 payload 时对齐 key：
  ```dart
  final payload = row.toJson();
  payload['scopeCsv'] = row.scope.map((s) => s.name).join(',');
  payload.remove('scope');
  ```

## 8. 【LOW】`markDirty` 定时器不随 provider 销毁取消

- **位置**：`providers.dart:136`
  ```dart
  void markDirty() {
    Future<void>.delayed(_debounce, () => syncNow());   // 无取消 / 无 disposed 守卫
  }
  ```
- **影响**：若 `SyncController` 在 3s 内被 dispose，`syncNow` 仍会跑并 `ref.read` 已销毁的 ref，
  抛 "Cannot use ref after disposal"（被 `syncNow` 的 try/catch 兜住，仅后台同步报错，不致命）。
- **建议**：存 `Timer` 并在 `build`/dispose 时 `cancel()`，或 `syncNow` 开头判 `ref.notifier` 是否仍挂载。

## 10. 根因归纳 & 建议的架构修正

1. **统一契约**：outbox payload 的 schema **必须等于**同步引擎消费的规范实体 map
   （`_bookToMap` / `_progressToMap` / `_ruleToMap` / `_collectionToMap` / `_membershipToMap`）。
   现在 book 手写、`progress` 手写、`rule` 用 `HighlightRule.toJson`、`collection/membership` 手写，
   各自漂移。最干净的做法是**用规范 map 直接生成 outbox payload**，而不是再写一份序列化。
2. **`mergeEntity` 必须区分"远端缺字段"（未改）与"远端显式置空"**（§2 修复）。
3. **删除统一靠 `remote['deleted'] == true`**，所有 delete payload 带 `deleted:true`。
